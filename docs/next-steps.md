## 2. 作業候補（優先度の案つき）

1. **`!workers` の重複排除（小〜中）**：更新中は旧・新 Gateway が同じ MESSAGE_CREATE を受けるため、Gateway 内の集合では防げない。Core 側 `SeenIds` を通す要求（source_id 付き）にする設計が必要。`!count` / `!ping` の経路は既に Core で重複を捨てる。
2. **Core の要求期限（B3、大）**：止まったハンドラを期限で打ち切りたいが、`WorkerTasks::request` のキャンセルが状態を壊す恐れがある。方針を決めないと入れられない（Q2）。
3. **Core の無停止差し替え（separate）（大）**：現状は Core の更新に botd の再起動が必要。Gateway の更新と同じ段階（standby → activate）を Core に作る設計が要る。
4. **孤児の再採用（中〜大）**：botd が死ぬと Core も失われる（stdin EOF で終了）。再採用には Core を botd から切り離す設計と、認証の引き継ぎが要る。
5. **改ざん検知付き監査（中）**：現状の `gateway-update-audit.jsonl` は追記のみで、改ざん検知と世代付きローテーションがない。
6. **複数シャード・長時間の実機検証（ユーザー作業が必要）**：現状の実 Discord の確認は 1 シャード。
7. **Interaction（スラッシュ）の重複の実機確認（ユーザー作業が必要）**：Discord の単一 ACK 規則に頼る想定が未検証。

私の案：結果が良ければ 1 → 5 → 3。2 と 4 は方針決定後。

## 6. Astra の設計レビュー（2026-11-16、read-only、gpt-6-astra）

優先度の見直し：**§2 の「1 → 5 → 3」を、実機検証（6・7）と障害時の診断・CI の安定化、次に `!workers` の重複排除と B3 の観測、最後に Core の無停止差し替え、に改める**。監査の保持と応答性は改ざん検知より先。孤児の再採用は後回し。

- **`!workers`**：`message.id` を持つ型付き診断要求を、同じ channel キーで同じ Core に流し、Core の重複判定を通してから既存の `ResponseGuard` / `ApiResult` で送る。罠：HTTP の結果が不明な段階で ID を確保すると返信が抑止され得る（有界な重複抑止であって配送保証ではない）。再起動で `SeenIds` は消える。
- **B3**：まず警告のしきい値だけ入れ、元の要求を待ち続ける（打ち切りはしない）。ハンドラは `mem::take` で状態を持つため、タイムアウトだけの (b) は現状安全ではない。強い回復は、受付を止めて監視側が Core を終了・回収し、最後の確認済みチェックポイントから復元する（途中の副作用は「結果不明」として自動再送しない）。
- **Core の無停止差し替え**：Gateway は接続したまま、Core を 1 スロットずつ入れ替える。候補は別の endpoint で token なしで準備、受付を有界に保留して drain、snapshot/復元、経路を切り替えて旧 Core を退役。drain に失敗したら切替前に中止。既存の handoff の障壁（`worker.rs:2344` 付近）を使う。罠：snapshot は `SeenIds` と任意の framework 状態を含まない。新 Core が処理を始めた後に旧 snapshot を再開しない。
- **抜けていたもの**：障害の行列（botd の SIGKILL、監査・チェックポイントのディスク満杯、止まったハンドラ、activate 失敗後の再試行）。監査・ローテーションの同期 I/O を監視ループの外へ。診断には操作 ID、`pending_audit`、Gateway／候補／Core のログも必要。孤児の再採用には systemd の `KillMode=mixed`（残りの子を終了する）の変更も要る。ローカルのハッシュ連鎖は、独立して信頼できるチェックポイントがないと書き換えを検知できない。CI の失敗は原因を追うまで「不明」として扱い、再実行で通ったことを根拠にしない。
- **質問の言い換え**：Q1：まず観測つきで 1 回更新し、その後 6 時間の soak。繰り返しは Identify の残り（Bot あたり 10 回/時、候補と回復を含む）で決める。`update-check.sh` は 1 シャード前提。Q2：許容する停止時間、失うチェックポイント、結果不明の副作用の扱いを聞く。観測を先に。Q3：重複排除を入れる（読み取り専用の診断として扱う）。Q4：ギルド数ではなく「両方のシャード ID に当たる通信を出せるか」。Q5：所有権・取消・永続化・認証の変更ごとにレビュー、それ以外は節目のみ。Q6：移動する branch の自動 pull ではなく、固定した成果物・checksum・戻し手順つきの、運用者が承認するスクリプト。
