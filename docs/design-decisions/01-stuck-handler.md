# 01. 止まったハンドラ（B3）

> **2026-11-17 の注記：** 対応案 B（自動再起動）は DDR-0003、0004 で**合意されていない**。DDR-0002 が求める「daemon からの停滞の照会」「診断情報」「開発者向け API」は**未実装**。差分は [reconciliation-with-ddr.md](reconciliation-with-ddr.md) を参照（本文は未修正）。

## 何が問題か

ハンドラ（コマンドを処理するコード）が終わらなくなると、その要求は Core の中でずっと完了しません。その間、**その Core の担当分が進まなくなります**（1 つのシャードに Core は 2 つあり、別の Core は動き続けます）。

## 本当に起きるのか

- **私たちが用意した処理（`!ping`、`!count`）では、起きていません。** Oracle の約 18 時間で `worker_unavailable` は 0 件、WSL の各種試験でも起きていません（出典：`docs/progress.md`）。
- 起きるのは、**利用者が書く処理**の中です。たとえば、外部の API を待ち続ける、データベースの応答が返らない、無限ループ、などです。discord.py の Bot でも、同じ原因で「コマンドが返事をしなくなる」ことは起きます。

## 起きたときに強制停止などの措置ができるか（現状・確認済み）

| 段階 | 現状 |
|---|---|
| 気づく | **できる。** Core が、30 秒以上完了しない要求を、標準エラー（`core-N.log`）に警告として出す（`要求が 30 秒以上完了していません（経過 N 秒、未完了 M 件）`）。同じ要求の再警告は 5 分以上空ける。要求は打ち切らない。実装：`src/src/worker.rs` の `observe_request`。実時間の短い値の単体テストあり |
| 手動で止める | **できる。** その Core を `kill -9` すると、botd が約 1〜2 秒で再起動する。状態は最後に保存した内容から復元される（実機：WSL と実 Discord、`!count` が巻き戻らず継続）。Bot やシャード単位の停止・再起動は `botctl stop|restart BOT [--shard N]`（`--force` は `--yes` が必要） |
| 自動で止める | **できない。** 「止まった」と判断して自動で再起動する仕組みはない |

## なぜ「打ち切るだけ」ではいけないか

いまの作りは、処理が始まるとき、Core の状態を**処理の側が丸ごと借り出し**（`mem::take`）、終わったら返します。ノートを借りて書き込むようなものです。借りた側を途中で取り消すと、**ノートが戻ってきません**（状態が失われる）。外から要求を取り消すのが危険な理由は、これです（出典：`docs/known-limitations.md`、B3 の記述）。

## 対応案

| 案 | 内容 | 確認の方法・注意 |
|---|---|---|
| **A. 観測のみ（実装済み）** | 警告を出すだけ | 実機で止まった処理を意図的に作り、警告が出るか確認する（未実施） |
| **B. 一定時間で、その Core を自動再起動** | 例：120 秒止まったら Core を終了し、botd が再起動、最後に保存した状態から復元。受け付けを止めてから落とし、中断された処理は「結果不明」として扱い、自動で再実行しない | 実装は小さい。注意：その Core の他の処理も巻き込まれる。中断された処理が外部に作用していたか分からない。**設定で有効にできる任意の機能**にするのが安全 |
| **C. コピーで作業してコミットする方式** | 状態の借り出しをやめ、コピーで作業して最後に書き戻す → [02](02-copy-on-commit-state.md) | 根本対応。設計と実装が大きい |

## 決めること

[decisions-needed.md](decisions-needed.md) の D1。特に、(1) 何秒で「止まった」とするか、(2) 結果不明になった処理の扱い、(3) B を入れてよいか。

## 試験の計画（B を入れる場合）

- 意図的に止まる処理を持つ Worker（試験用）で、警告が出て、設定した秒数で Core が再起動し、`!count` などが継続すること。
- 再起動の直前に処理中だった要求が「結果不明」として記録され、再実行されないこと。
- 再起動を繰り返しても、Identify の予算を消費しないこと（Core の再起動は Gateway の Identify を使わない）。
