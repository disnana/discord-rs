# 02. 状態を「コピーで作業してコミット」する案

ユーザーの発案（「管理元を移す、原子的なロックのような仕組みはできないか」）を、具体的な設計案にしたものです。**方向は正しく、B3（止まったハンドラ）の根本対応の入口**です。

## いまの作り（確認済み）

処理が始まると、Core の状態を処理の側が**丸ごと借り出し**（`mem::take`）、完了後に返します。同時に 1 つの処理しか状態を触れません（排他）。取り消すと、借りた状態が戻らないため、外から取り消せません。

## 提案する作り

1. 状態にバージョン番号を付ける。
2. 処理が始まるとき、**状態のコピー**と、そのバージョン番号を渡す（借りない）。
3. 処理は、コピーに対して作業する。
4. 完了時に、**「元の状態のバージョンが、コピーを取ったときのままなら、一括で書き戻す」**（コミット。CAS という比較して置き換える方式）。変わっていたら、衝突として扱う（再試行か、拒否）。
5. 取り消し（打ち切り）は、コピーを捨てるだけ。**元の状態は無傷**。

## 利点

- 止まった処理だけを、安全に打ち切れる（Core の再起動が要らない）。
- 状態が中途半端な書き換えのまま残らない。

## 限界・難しい点

1. **外部への作用は取り消せない。** 処理が返信を送った後に取り消すと、状態は元に戻るが、返信は送られたまま。→「結果不明」として明示する（自動の再実行はしない）。
2. **同時に来た処理の衝突。** 2 つの処理が同じ状態のコピーを取り、片方が先にコミットすると、もう一方は衝突する。選択肢は、(a) 同じキー（チャンネルなど）の処理は直列にする（いまの排他に近い）、(b) 衝突したら再試行する（再試行が副作用を二重にしない設計が要る）。**どちらを取るかは未決定。**
3. **コピーの費用。** カウンタなどの小さい状態は問題ない。大きい状態は、差分で持つなどの工夫が要る（未検討）。
4. 「全体で 1 つの数」のような共有の状態の扱い（キーごとに分ける設計との関係）。

## 評価・次の一手

- 設計として検討する価値がある。実装は、`WorkerTasks::request` と Core のハンドラ周り（`src/src/worker.rs`）に広く触れる。
- 次の一手：(1) 衝突の方針（直列か、再試行か）を決める。(2) 小さい試作（カウンタの状態だけ）で、打ち切りと元の状態の維持をテストで示す。

## 不明な点

- 利用者が書く Bot の状態（cog の状態）に、この方式が自然に使えるか（利用者の API の形に影響する）。
- 同時に来る処理の実際の頻度。
