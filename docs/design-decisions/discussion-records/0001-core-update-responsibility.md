# DDR-0001: Core更新時の責任分界と任意の状態引き継ぎ

- 日付: 2026-11-16
- ステータス: **議論で合意した方針**（実装済み・テスト済みの意味ではない）
- 対象: discord-rs Core無停止更新
- 注意: 既存実装と異なる可能性がある。実装状況はコード・テストで別途確認する。

## 合意事項

1. **基盤とBot開発者の責任を分ける。** discord-rsはプロセス管理、イベント配送、切り替え、draining、および任意の引き継ぎ手段を提供する。アプリ固有のデータの意味、永続化、業務上の副作用と冪等性の管理を無条件に引き受けない。ただし基盤自身の配送・更新の不具合は開発者に転嫁しない。
2. **正常な更新では旧Coreが処理を完了する。** 旧Coreが引き受けた処理は原則旧Coreで終わらせる。新Coreの準備が整った後、新しい処理の配送先を切り替える。旧Coreは新規受付を停止し、処理中タスクをdrainingしてから終了する。
3. **全Botに旧Core→新Coreの業務状態移送を強制しない。** 状態引き継ぎが不要なBotは、状態移送なしで更新できる。
4. **開発者向けの任意引き継ぎ機能を設ける方向で合意。** 引き継ぐ内容・形式・整合性条件はBot開発者が指定する。基盤は受け渡しの機構を提供する。
5. **引き継ぎ失敗時は更新を中止し、旧Coreによる稼働を維持する方針。** この保証が成立するよう、不可逆な配送切り替えより前に失敗を検出・ロールバックできる設計を詰める。切り替え後の失敗の扱いは未決定。
6. **目標は安全な無停止更新と開発しやすいAPIの両立。** 正常な更新と、旧Coreのクラッシュなど予期せぬ障害時の復旧保証は混同せず別に定義する。

## 今後の検討案（未合意）

- 任意の引き継ぎフックの名前例: `on_handoff()` と `on_restore()`。API名、型、実行順序はいずれも**未決定**。
- 旧Coreが実行中のタスクをどう追跡するか、完了をどのように判定するか。
- 新Core準備確認、引き継ぎ、配送切り替えの正確な順序と、失敗時のロールバック可能範囲。
- ハンドラが終了しない場合の待機期限や開発者への通知。
- 状態引き継ぎのサイズ上限、バージョン互換性、整合性。
- Gatewayセッションの維持、イベント重複・欠落、突発的な障害時の扱い。
