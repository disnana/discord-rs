## 経緯

Astra と Sol が、ウェブ検索つきで設計をレビューし、2 人はほぼ同じ結論に達した（review-2026-11-17-astra-sol.md）。Claude の実測でも、P1 の「ディスク上の状態ファイル」方式は、ユーザーの条件（I/O 負荷が最低限）を満たさなかった（アイドルの Core で 300 秒に書き込み 84 回、ディスクへ 98,304 バイト。状態ファイルなしの制御実験は 0）。Claude が 3 つの推奨を出し、ユーザーが **「その案で言っていいよ」** と回答した。

## 了承した内容

### 1. P1 のテレメトリは、tmpfs 上のファイルにする
- Core の状態ファイルを、**ディスクではなく、tmpfs（`/run/discord-rs/` 配下）に置く**。ディスクへの書き出しをゼロにする（ユーザーの条件）。
- **起動時に、置き場所が本当に tmpfs かを確認し、そうでなければ機能を無効にする**（ディスクには書かない）。本番は、systemd の `RuntimeDirectory=discord-rs` で作る。
- **壁時計をやめ、単調時計（`CLOCK_BOOTTIME`）**を使う。記録に、**Core の起動ごとの識別子（世代）と、書き込みの連番**を入れる。botd は、自分が起動した Core の PID と一致するかも確認する。
- 表示は**「停滞の疑い」**（確定ではない）。設計書の「30 秒に最大 1 ページ」「CRC が破損をすべて検出」という表現は削除・訂正する。
- ノンブロッキングのパイプ方式は、tmpfs で足りなければ後で検討する（いまは採用しない）。
- **実装後に、I/O を実測し、ディスクへの書き出しが 0 であることを確認する**（確認できなければ、やり直す）。

### 2. Core 切り替え時の、重複排除の記憶の引き継ぎ（DDR-0006 の提案 1 を置き換える）
- **順序：** 準備 → **受け付けの壁（admission barrier）** → **最終の重複排除の記憶を渡す** → **復元の確認（ACK）** → **配送の切り替え（commit）** → 旧 Core の退役。
- **失敗したときは、切り替え前に中止する**（旧 Core のまま稼働を続ける）。**これが既定。** 明示的に許可したときだけ、劣化したまま続ける。劣化している状態は、運用上の状態として、はっきり見えるようにする。
- 重複排除の記憶は、**集合ではなく、追い出しの順序つきの窓**として渡す。`SeenIds` は実行の前に ID を記録するので、「完了した処理の台帳」ではない（その意味を設計書に明記する）。
- 旧 Core の、HTTP の結果の受領（`ApiResult`）は、受領されるまで、旧 Core の接続を保つ。受け付けの停止が、受領の経路を止めてはいけない。
- シャードごとに、Gateway の更新・Core の更新・復旧・管理操作を直列化する。**Core の数の変更は拒否する**（配送先の計算が変わる）。
- DDR-0006 の「引き継ぎに失敗しても更新を止めない」は、**この記録で取り消す**（DDR-0001 の「引き継ぎ失敗時は更新を中止し、旧 Core による稼働を維持する」と一致させる）。

### 3. 作業の優先順位
1. P1 を tmpfs 方式に直し、I/O の実測で 0 を確認する。
2. `03-core-hot-swap.md` を、受け付けの壁の手順で書き換える（文書のみ）。
3. **P3（認証・監査つきの手動復旧）を、差し替えの実装より先に。** 退役中の世代の数に上限を設ける。
4. **Identify の実際の送信を、Bot ごとに 1 つのスケジューラーで調整する**（起動・手動・復旧の経路を含む）。
5. nonce の再試行（操作ごとに固定した nonce、本文全体の JSON、UnknownOutcome の保持）。**先に、実機の 2 回投稿の試験が要る（投稿先と許可が要る）。**
6. Core の差し替えの実装（1〜4 の後。シングルの完成後）。

**随時行う小さい修正：** Gateway のログの時刻を、ミリ秒まで出す。文書の不正確な記述の訂正（1006 の意味、discord.py の nonce の挙動、「すべて 1 秒以内」の限定）。
