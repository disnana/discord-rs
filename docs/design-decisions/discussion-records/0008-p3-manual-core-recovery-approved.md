## 経緯
Claude が設計案（p3-manual-core-recovery-design.md）の 9 章の決定事項と推奨案を、チャットで説明した（ユーザーが設計書を直接見られなかったため）。ユーザーは「**いいんじゃね**」と回答した。

## 了承した内容（9 章の推奨案どおり）
- **D-P3-0：** コマンドは `botctl core restart <BOT> --shard N --core K`（仮名のまま）。
- **D-P3-1：** 権限は、当面 `admin`（＋ shard の scope）のみ。復旧専用の role は P3b で検討。
- **D-P3-2：** 手動の再起動の制限は、スロットごとに、間隔 60 秒以上、15 分に最大 3 回（初期値）。
- **D-P3-3：** 退役中の世代は、スロットごとに最大 1。
- **D-P3-4：** 停滞の疑いがない Core の再起動は、`--force` つきで許す（監査に残す）。`--force` でも回数制限は外さない。
- **D-P3-5：** 終了の依頼から強制終了までの猶予は 5 秒。
- 対象の固定（incarnation id）、排他、「最後の稼働中の Core」の確認、要求を先に監査へ記録、botd 自身の `Child` のハンドルでの終了は、設計案のとおり。

## まだ決まっていないこと
- 停滞した Core が stdin の EOF に反応するか（実験で確認する）。
- 既存の `operation` 照会に載せるか、同期の応答にするか（実装時に決める）。
- 復旧専用 role の名前と範囲（P3b）。

## 実装担当 AI への注意
- 方針の了承であり、実装済み・検証済みではない。
- 「復旧できる」は、実機で停滞した Core を復旧し、`!count` が続くことを確認するまで書かない。
- 強制終了した Core の処理中イベントの完了、未受領の REST の結果、重複排除の記憶の保持は、**保証しない**。
