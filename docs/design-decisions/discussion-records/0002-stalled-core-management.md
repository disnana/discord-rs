# DDR-0002: 停滞Coreの監視と安全な管理操作

- 日付: 2026-11-16
- 状態: **議論で合意した設計方針**（実装済み・検証済みではない）
- 関連: [DDR-0001](0001-core-update-responsibility.md)、[01-stuck-handler](../01-stuck-handler.md)

## 合意事項

1. **正常なCore無停止更新で、処理中の旧Coreを警告だけで強制終了しない。** 新Coreへの新規処理配送を維持し、旧Coreは処理完了までdrainingする。長時間未完了の処理は警告・状態確認の対象とする。
2. **異常や停滞はDaemon側から確認できるようにする。** 管理者はCLI等で警告、対象Core、経過時間、更新の状態を調べられる。
3. **Bot開発者が警告をプログラムから利用できるようにする。** 通知先や通知処理はBot開発者が選ぶ。イベント購読や状態照会などの具体的APIは未決定。
4. **通知だけでなく管理操作の自動化を可能にする。** 開発者のコードから、権限の範囲内でCoreの停止・再起動などをDaemonへ要求できる経路を提供する。障害中のBot自身に依存しない管理経路も用意する。
5. **共通のDaemon管理インターフェースを設け、CLIとプログラム用APIで管理ロジックを共有する。** プログラムが直接OSプロセスをkillすることを基本設計としない。
6. **安全性を担保する。** 管理操作には対象の識別・世代確認、権限検証、更新処理との競合防止、操作の監査、再起動の無限ループを防ぐ制限などを検討・実装する。具体的な方式は未決定。

## 境界と注意

- 警告の観測と管理操作の機構は基盤側の責任。通知先の選定、通知メッセージ、運用判断の自動化ロジックは原則として開発者の責任。
- Coreがハングした場合にも、Daemonが管理できることを目指す。ただしホスト全体の障害やDaemon自身の停止まで、この合意だけで回復保証しない。
- 「旧Coreを待機させる」方針は正常更新の原則。新旧切り替えの具体的な排他・drainingの可否は実装とテストで確認する必要がある。
- 実装が存在することを本記録から推定しない。既存CLIや監視機構と統合する際には現行コードと整合を確認する。

## 未決定（次に検討）

- 旧Coreを停止・再起動する際の世代ID／操作IDと fencing の具体的手順
- 操作要求の認証・認可、失敗・再試行の意味、タイムアウトと監査項目
- 警告の発生条件、解除条件、イベント配送の信頼性・バッファ
- Core停止を伴う手動・自動操作を旧Coreのdrainingとどう整合させるか
