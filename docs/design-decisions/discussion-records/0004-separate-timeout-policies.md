# DDR-0004: 処理タイムアウトと旧Core退役タイムアウトの独立設定

- 記録日: 2026-11-16
- ステータス: **議論で合意した方針**（実装・検証済みではない）
- 関連: [DDR-0003](0003-old-core-timeout-diagnostics.md)

## 合意事項

**個々の処理の経過時間**と、**旧Core全体が退役を待っている時間**を、別々に管理し、それぞれ独立に設定できるようにする。

1. **処理単位のタイマー:** 個別ハンドラ／要求の処理開始からの経過時間を観測する。長時間の処理を検知し、対象の処理名・Core世代・開発者コードの識別情報などを診断情報として公開する。
2. **旧Core退役タイマー:** 更新により旧Coreがdraining状態に入ってからの経過時間を観測する。退役が長引いた際に警告し、明示的に有効化された場合だけ旧Coreの自動停止を行える。
3. **独立設定:** それぞれの警告閾値・動作は別々に設定できる。片方の警告を、もう片方の強制停止の直接トリガーと混同しない。
4. **既定は非破壊的:** 警告だけで旧Coreを強制終了しない。自動停止は任意設定とする。自動停止は「退役対象の旧Coreの停止」であり、再起動ではない。
5. **誤操作の防止:** 自動停止前には対象CoreのID、世代、draining状態、現在の更新操作との対応をDaemon側で再確認し、新Coreや無関係のCoreへ作用しないようにする。

## 設定例（提案であり確定したAPIではない）

```toml
[core.handler_timeout]
warning_after = "30s"

[core.retirement_timeout]
warning_after = "60s"
auto_stop = false
stop_after = "300s"
```

数値、設定キー、適用範囲はすべて例示。正式な既定値・設定仕様は未決定。

## 未決定事項

- タイマーの基準時刻、再接続や更新中断における挙動
- Bot単位、Core単位、ハンドラ単位など設定の継承と上書き
- 自動停止時の未完了処理の結果不明の記録、ログと通知の形式
- 退役対象がなくなったときのタイマー停止、古い警告の解消
- 実装状態とテストケースの検証

## 実装担当AIへの注意

合意したのは「2種類を独立に管理・設定できる」こと。個別ハンドラのタイムアウトで処理を自動キャンセルすることや、旧Coreを自動再起動することは合意していない。
