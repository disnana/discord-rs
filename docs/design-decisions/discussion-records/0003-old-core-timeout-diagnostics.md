# DDR-0003: 旧Coreの停滞診断と任意の自動停止タイムアウト

- 記録日: 2026-11-16
- 状態: **設計議論で採用した方向性**。詳細仕様・実装・検証は未完了。
- 関連: [DDR-0001](0001-core-update-responsibility.md)、[DDR-0002](0002-stalled-core-management.md)

## 追加の合意事項

1. 無停止更新のため退役待機中の**旧Core**について、何の処理が長引いているか、どの開発者コードに対応するかを調べやすくする。CLI/Daemon管理面および開発者が利用できるAPIから診断情報を取得できる方向で設計する。
2. **処理のタイムアウト時間を設定できるようにする。** 警告を出す条件と、旧Coreを最終的に停止させる条件は別に扱う。
3. **タイムアウトに達した旧Coreを自動停止させる機能はオプション**とする。既定動作では長時間処理を理由に強制終了せず、警告しながらdrainingを継続する。
4. この自動操作は更新中の**旧Coreを退役させるための停止**であり、旧Coreの再起動を意味しない。新Coreや正常な別のCoreを巻き込まないよう対象と世代を再確認する。
5. 旧Coreを強制終了すると未完了の業務処理が中断され、結果不明となりうる。その危険性を設定・ログ・APIで明示する。

## 診断情報の設計候補（フィールドは未確定）

- Bot / shard / Coreの識別子と世代
- 要求・ハンドラの識別子、コマンド名または開発者指定の処理名
- 開始時刻、経過時間、警告またはタイムアウトの条件
- 可能ならハンドラの**登録位置**や開発者が指定した計測ポイント

**注意:** 非同期タスクで「まさに現在停止しているソースコード行」を常に特定できるわけではない。登録位置やトレース地点を報告できることと、現在実行行の厳密な特定を混同しない。

## 未決定事項

- timeoutを個々の要求の処理時間に対して測るか、Core全体のdraining待機時間に対して測るか。両方を別設定にするか。
- 設定単位（Bot、Core、ハンドラなど）、既定の警告秒数、停止秒数。
- 停止前の再確認手順、更新状態・世代IDの比較、権限の具体的な検査方法。
- 警告や診断情報の保持期間、購読API、公開範囲、機密情報のマスキング。
- 実装が現在どこまで存在するかの確認と、障害注入を含むテスト。

## AI実装担当への注意

合意済みなのは「長引く処理の診断を可能にする」「設定可能なタイムアウト」「任意の自動**停止**」という方向性。未決定事項を勝手に確定した仕様として扱わないこと。特に自動再起動と読み替えないこと。
