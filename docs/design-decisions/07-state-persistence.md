# 07. 状態の保存（最大約 2.5 秒の窓）

## 何をしているか（確認済み。出典：`docs/known-limitations.md`）

- Core は、カウンタなどの状態を**メモリ**に持つ。再起動するとメモリは消える。
- そこで、Gateway が「確認済みのスナップショット」を、`--state-path` 配下の `core-state.json` に書き出す。Gateway や botd が再起動したら、ここから新しい Core に状態を戻す。
- 書き出しの条件：**変化があったときだけ、最短 2 秒の間隔で**。原子的な書き込み、権限 0600、大きさの上限 1 MiB。停止時は最終状態を書く。
- 何を保存するか：**`!count` と `!job` のデモ用の状態だけ**（snapshot-v3）。**利用者が書く Bot の状態（cog の状態、フレームワークの StateStore）は含まない。**

## 「約 2.5 秒の窓」とは

`kill -9` のように突然落とされると、**最後に書き出した後の変化**（最大 約 2.5 秒分）が失われる。例：カウントが 70 で保存され、その後の 2 秒に 3 回コマンドを送ってから落とすと、73 ではなく 70 に戻り得る。

実機の試験（WSL・実 Discord）では、`kill -9` の後も `!count` が巻き戻らず続いた（落とす前に書き出されていた）。ただし、書き出しの間隔の内に落とす試験は、意図的にはしていない（未確認）。

## 何が失われ、何が失われないか

| 項目 | 突然の停止（`kill -9`）の後 |
|---|---|
| 最後に書き出した状態 | 残る |
| 書き出し後、約 2.5 秒以内の変化 | 失われ得る |
| 正常な停止（SIGTERM、`systemctl stop`）の直前の状態 | 最終状態を書くので残る |
| イベントのジャーナル（処理の履歴） | 保存しない |
| 利用者の Bot の状態（StateStore） | この仕組みの対象外（別の仕組み） |

## 選択肢

| 案 | 内容 | 利点 | 欠点 |
|---|---|---|---|
| A. 現状 | 変化時、最短 2 秒間隔 | 書き込みが少ない | 窓がある |
| B. 間隔を短くする | 例：変化のたびに書く | 窓がほぼなくなる | ディスクへの書き込み（確実に書くための待ちを含む）が増える。デモ用の小さい状態なら許容できる可能性 |
| C. ジャーナル（変化の履歴）を作る | 変化を追記し、復元時に再生 | 窓がなくなる | 設計が大きい |

## 重要な論点：利用者の状態（StateStore）

- 本番の Bot では、**利用者が書く状態の保存**の方が重要。フレームワークの `StateStore`（TTL・容量・CAS・スキーマを持つ非同期 API。メモリとファイルの実装）はあるが、「プロセスやホストの障害を越えて保持される保証はない」と記載されている（出典：`docs/known-limitations.md`「API・状態・IPC」）。
- 実 Discord・実際の障害での検証は、不十分。

## 評価・推奨

- この仕組みは**デモ用の状態の話**なので、窓の短縮の優先度は低い。
- 優先するのは、**利用者の状態（StateStore）の、障害後の復元の検証**。
