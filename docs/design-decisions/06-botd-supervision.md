# 06. botd が死んだときの動きと、子プロセスの引き継ぎ

## botd とは

Bot の「管理人」。シャードごとに Gateway と Core（2 つ）を起動して見張り、落ちたら再起動する。systemd からは 1 つのサービス（`botd`）として動く。

## いまの動き（確認済み。WSL・実 Discord で `kill -9` した結果）

1. botd が死ぬと、**Core は自分で終了する**（botd との接続が切れたら終了する作り。stdin が閉じる）。Gateway も systemd の制御グループで止まる。
2. systemd が、約 **5 秒**で botd を再起動する。
3. 新しい botd が、古い起動予約を整理し、Core と Gateway を新しく起動する（PID がすべて入れ替わる）。
4. 状態は、Gateway が保存していたスナップショットから復元される（`!count` は巻き戻らず継続。→ [07](07-state-persistence.md)）。

出典：`docs/progress.md`（2026-11-16 午後と夜）、`docs/known-limitations.md`。

## ユーザーの案の整理

「botd が監視で PID を使って、自動で止めるなどの管理ができれば」

- **「親が死んだら子が止まる」は、すでにある。** 見張る人のいない Core が動き続けるのは危険（誰の管理下でもなくなる）なので、そうしている。
- **逆向き（子を生き残らせ、新しい botd が引き継ぐ。再採用）は可能だが、慎重な設計が要る。**

## 再採用（引き継ぎ）の論点

| 論点 | 内容 |
|---|---|
| PID の再利用 | PID だけで「あの Core だ」と判断するのは危険。プロセスの開始時刻や、通信での秘密の確認が要る |
| 二重の botd | 2 つの botd が同時に動くと、同じ Core を取り合う。ロックファイルで 1 つに限る |
| 秘密の引き継ぎ | Core の接続の秘密（`core.secret`）を、安全に新しい botd へ渡す |
| systemd の設定 | 子を一緒に終了する設定（`KillMode`）を変える必要がある |
| 残った子の見分け | 古い世代の Core と、新しい世代の Core の区別（番号） |

## 利点と費用

- 利点：botd の異常終了時の 5 秒の停止と、状態の巻き戻りがなくなる。
- 費用：上の論点の設計と試験。誤って古い Core を引き継ぐ危険。

## 評価・推奨

- botd は小さく、**一度も落ちていない**（Oracle の約 18 時間、WSL の試験でも自然には落ちていない）。利点が小さいので、**後回しを推奨**。
- 代わりに、systemd の `Restart=` の設定と、再起動後の自動復旧を、実機で確認することを優先する（OS 再起動後の自動起動は、まだ未確認。[unverified-items.md](unverified-items.md)）。
