# 03. Core の無停止差し替え（分離モード）

> **2026-11-17 の書き換え：** DDR-0001（状態の引き継ぎは任意。正常な更新では、旧 Core が受け付けた処理を完了し、新 Core が新規を担当する）、[DDR-0007](discussion-records/0007-p1-tmpfs-and-cutover-order.md)（切り替えの順序と、失敗時の中止）、[Astra と Sol のレビュー](review-2026-11-17-astra-sol.md)に合わせて、**全面的に書き直した**。以前の骨子（「キーごとに状態を必ず新 Core に渡す」）は、廃止した。**未実装。** 実装は、シングルの完成後（優先順位 6）。

## 現状（確認済み）

- Gateway の更新は無停止（`botctl gateway-update`。待機 Gateway を起動して引き継ぐ）。
- **Core の更新は、botd の再起動が必要**で、Bot は数秒止まる（出典：`docs/known-limitations.md`、`docs/progress.md`）。
- 組み込みモード（embedded）の Worker 更新には、すでに「旧世代の処理と応答を保持しつつ、新世代へ配送する」仕組みがある（出典：`docs/known-limitations.md`「Worker更新・配送・外部副作用」）。ただし、任意のアプリ状態や Future は移さず、保存の対象は限定されている。
- **配送先は、キーから決定的に決まる**：`(key ^ (key >> 22)) % Core の数`（`src/src/worker.rs` の `dispatch_key*`）。
- **HTTP の結果の受領（`ApiResult`）は、応答を発行した世代の Core の接続に固定される**（`finish_response`。`response.generation.process` に送る。`src/src/worker.rs`）。
- 重複排除の記憶（`SeenIds`、直近 4,096 件）は、Core のメモリ上にあり、**処理を実行する前に ID を記録する**（完了した処理の台帳ではない）。再起動をまたいでは検出しない。スナップショット（`core-state.json`）には含まれない。
- Core は、**高い epoch の接続が来ると、いま処理している接続を締め出す**（要求と要求の間に効く。`src/src/core_server.rs`）。

## 目標と責任の分け方（DDR-0001）

- **正常な更新では、旧 Core が、すでに受け付けた処理を完了する。** 新 Core の準備が整った後に、**新しい処理**の配送先を切り替える。旧 Core は、新規の受け付けを止め、処理中のタスクを終わらせてから（drain）終了する。
- **業務状態の引き継ぎは、全 Bot に強制しない。** 必要な開発者が使える**任意の引き継ぎ**（フック。`on_handoff` / `on_restore` は仮名）を提供する。基盤は、受け渡しの仕組みを提供する。
- **基盤自身の状態**（重複排除の記憶）は、基盤の責任で引き継ぐ（DDR-0006、DDR-0007）。
- **引き継ぎに失敗したら、更新を中止し、旧 Core で稼働を続ける**（DDR-0001、DDR-0007）。

## 切り替えの手順（DDR-0007 の順序）

**1. 準備（やり直せる。ここまでの失敗は、すべて中止して旧 Core のまま）**
- 新 Core を、旧 Core と**別の IPC ソケット**で起動する（Bot の token は渡さない。Core に token を渡さない方針を維持）。健全性の確認と capability の交渉。
- 新 Core の Core の数・配送のハッシュ・キーの取り出し方が、旧 Core と**同一**であることを確認する。**Core の数を変える更新は、この手順では拒否する**（配送先の計算が変わる。別の移行の手順が要る。未設計）。
- 開発者が任意の引き継ぎを指定している場合：旧 Core がスナップショットを出し（`on_handoff`）、新 Core が復元する（`on_restore`）。**失敗したら中止。** ただし、旧 Core は、この間も動いているので、スナップショットの後に起きた変化の扱いは、「受け付けの壁」で定める（下記 2）。

**2. 受け付けの壁（admission barrier）**
- 旧 Core が、**新しい要求の受け付けを止める**。すでに受け付けた処理は、旧 Core で続ける。壁の間の新しい到着は、**上限つきでバッファ**する（バッファの上限と、あふれたときの扱いは**未決定**）。
- 送信待ちの配送は、送る前に**世代を再確認**する（古い配送先に、壁の後の新しい処理を、誤って送らない）。

**3. 最終の重複排除の記憶を渡す**
- 旧 Core が、**重複排除の記憶を、追い出しの順序つきの窓として**（集合だけでなく）新 Core に渡す。壁を張った後なので、渡した後に旧 Core が新しい ID を受け付けることはない。

**4. 復元の確認（ACK）**
- 新 Core が、記憶（と、指定された場合は開発者の状態）を復元したことを、確認として返す。**確認が取れなければ、切り替えず、中止して旧 Core のまま**（壁を外し、バッファした要求を旧 Core に流す）。

**5. 配送の切り替え（commit）**
- 切り替え番号（epoch）を上げ、新しい処理の配送先を新 Core にする。旧・新どちらの Gateway も、同じ規則で配送先を決める。バッファした要求を、新 Core に流す。**この境目より後の失敗の扱いは、下記**（仕様 `architecture.md` §6 の動作ルール 5 に従う）。

**6. 旧 Core の退役（drain）**
- 旧 Core は、新規を受け付けず、処理中のタスクが終わるまで待つ。**HTTP の結果の受領（`ApiResult`）が、すべて受領されるまで、旧 Core の接続を保つ**（受領は、発行元の世代に固定されているため。受け付けの停止が、受領の経路を止めてはいけない）。
- 退役タイマー（DDR-0004）：既定は**警告のみ**。`auto_stop` は、明示的に有効にしたときだけ（既定オフ。再起動ではなく、退役のための停止）。停止の前に、対象の ID・世代・drain 状態・現在の更新操作を再確認する。

## 切り替え後の失敗（DDR-0001 の未決定部分。**仕様 `architecture.md` §6 の動作ルール 5 に合わせる**。ユーザーの確認待ち）
- **仕様（architecture.md §6 ルール 5）：** 「健全性の失敗は、切替前なら旧 Core 続行。**切替直後の新 Core のクラッシュは、旧 Core が維持されている限り、ロールバック候補にできる**。ドレイン済み／旧版が既に終了した後は…（仕様の続きを参照）」。つまり、**旧 Core が drain 中で、まだ生きている間は、戻せる**。旧 Core が退役を終えた後は、戻せない。
- したがって：
  - **新 Core が、切り替え直後（旧 Core がまだ生きている間）に落ちた**：旧 Core へ配送を戻す（ロールバック）候補にできる。戻すか、通常の障害として botd が新 Core を再起動するかの判断基準は**未決定**（新 Core の再起動が速ければ、戻さない方が単純）。
  - **旧 Core が退役を終えた後に、新 Core が落ちた**：通常の Core の障害と同じ扱い（botd が再起動し、保存済みのスナップショットから復元）。戻れない。
  - **旧 Core が drain 中に落ちた**：未完了の処理は、**結果不明**として記録する（自動の再実行はしない）。
- **この文書の以前の記述（「切り戻さない」）は、仕様より強い主張だったので、訂正した**（Sol の指摘で、食い違いを確認）。DDR-0007 は「切り替え後の失敗は切り戻さず」とは書いておらず、「この境目より後の失敗は、別に定義する」としている。

## 並行する操作の直列化と、上限
- **シャードごとに、Gateway の更新、Core の更新、復旧、管理操作（P3）を直列化する。** Gateway の所有 epoch と、Core の世代は、別に持つ。切り替えの状態を記録して、クラッシュ後に復旧できるようにする。
- **退役中の世代の数に上限**を設ける。自動の停止をしない以上、止まった旧 Core が溜まるため、上限に達したら、新しい更新を拒否する。**上限の値は未決定。**
- **P3（認証・監査つきの手動復旧）を、この実装より先に作る**（優先順位 3）。

## 難しい点・未決定
1. **「全体で 1 つの数」（例：`!count` の値）。** DDR-0006 の方針では、デモ状態は、開発者向けの任意の引き継ぎフックを使う。フックが実装されるまでは、Core の更新で戻る（botd の再起動と保存済みスナップショットからの復元）。
2. **受け付けの壁の間のバッファの上限**と、あふれたときの扱い。
3. **壁を張っている時間の上限。** 長すぎると、Bot が応答しない時間になる。時間を超えたら、中止して旧 Core のまま（案）。
4. 重複排除の記憶の**窓の大きさ**（4,096 件は、トラフィック次第で数秒〜数分）。窓を大きくするか、引き継ぎに失敗しないことの保証をどうするか。
5. 更新中に Gateway が再接続・更新される場合の整合（シャードごとの直列化で、同時に起こらないようにする案）。
6. **重複排除の記憶が、完了した処理の台帳ではない**（実行の前に ID を記録する）こと。「見た」ことと「完了した」ことを区別する必要があるか。

## 他システムから学ぶこと（Sol、Astra）
- **取り入れる：** NGINX の「新しい受け付けを止め、既存の処理を終わらせる」（準備してから退役）。Erlang/OTP の「明示的な一時停止と、状態の変換」（開発者の任意の引き継ぎの境界）。
- **避ける：** Kubernetes の既定の「猶予の後の強制終了」（警告のみの方針と衝突）。
- systemd のソケット活性化は、ソケットを渡すだけで、状態や結果の受領は渡さない。

## 再利用できるもの
- 組み込みモードの世代の引き渡し（`worker.rs` の handoff の障壁）。
- Gateway の更新の段階（待機・有効化・確認・退役）と、epoch による締め出しの考え方。
- `finish_response` の、発行元の世代への結果の受領の固定。
