# 03. Core の無停止差し替え（分離モード）

> **2026-11-17 の注記：** 骨子の「キーごとに状態を必ず渡す」手順は、DDR-0001 の合意（**状態の引き継ぎは任意。正常な更新では旧 Core が受け付けた処理を完了し、新 Core が新規を担当する**）と調整が必要。DDR-0005 も同じ指摘をしている。差分と提案は [reconciliation-with-ddr.md](reconciliation-with-ddr.md) を参照（本文は未修正）。

## 現状（確認済み）

- Gateway の更新は無停止（`botctl gateway-update`。待機 Gateway を起動して引き継ぐ）。
- **Core の更新は、botd の再起動が必要**で、Bot は数秒止まる（出典：`docs/known-limitations.md`、`docs/progress.md`）。
- **組み込みモード（embedded）の Worker 更新には、すでに「旧世代の処理と応答を保持しつつ、新世代へ配送する」仕組みがある**（出典：`docs/known-limitations.md`「Worker更新・配送・外部副作用」）。ただし、任意のアプリ状態や Future は移さず、保存の対象は限定されている。

## ユーザーの提案（採用する方式）

**新しい Core を起動し、新しい通信は新 Core が処理を始め、旧 Core は処理が終わり次第止めて、完全に移行する。**

私が以前の説明で「受け付けを止めて」と書いたのは、安全側に寄せすぎでした。この方式（受け付けを止めない）が目標です。

## 設計の骨子（案）

1. 新しい Core を、旧 Core と別の IPC ソケットで起動する（Bot の token は渡さない。Core に token を渡さない方針は維持）。
2. Gateway が、新旧の両方の Core に接続する（重なりの期間）。
3. **キー（チャンネルなど、状態を持つ単位）ごとに、担当の Core を 1 つに決める。** 切り替えの開始後、新しいキーは新 Core、すでに処理中のキーは、旧 Core の処理が終わるまで旧 Core に固定（ピン留め）する。
4. 旧 Core で、そのキーの処理中の要求がなくなった時点で、**状態を新 Core に引き渡す**（スナップショットの復元）。引き渡し後、そのキーの担当は新 Core になる。
5. 旧 Core のすべてのキーを引き渡したら、旧 Core を停止する。
6. 引き渡しに失敗したキーは、旧 Core のまま維持し、切り替えを中止して旧 Core を継続する（失敗時に元へ戻せること）。

## 難しい点（調べ・決めるもの）

1. **「全体で 1 つの数」（例：`!count` のグローバルな値）の扱い。** 新旧の Core が同時に書くと食い違う。キーごとの担当に分けるか、引き渡しの間は短い待ちを入れるかの選択が要る。
2. **重複排除の記憶（`SeenIds`）は、スナップショットに含まれない**（出典：Astra の設計レビュー `docs/next-steps.md` §6。`src/src/core_state.rs` の保存項目にも該当がないことを確認）。新 Core に引き継ぐ必要がある。
3. **番号（epoch）の締め出しとの整合。** Gateway の更新で使っている仕組みとの関係を、設計で確認する。
4. 更新中に Gateway が再接続・更新される場合の整合。

## 再利用できるもの

- 組み込みモードの世代の引き渡し（`worker.rs` の handoff の障壁）。
- Gateway の更新の段階（待機・有効化・確認・退役）の考え方。

## 評価

- 作業は中〜大。シングルを完成させた後でよい。Core の変更を伴う更新のときだけ、数秒の停止がある、という影響。

## 次の一手

- 上の 1（全体の数の扱い）の方針を決める。
