## 提案 1：基盤自身が持つ状態（重複排除の記憶、デモ状態）の、新旧 Core の間での扱い

### 平易な例
郵便局に例えます。窓口（Core）が「処理済みの手紙の番号帳」を持っています（重複排除の記憶 `SeenIds`）。窓口を新しい建物に引っ越すとき、新しい窓口が番号帳なしで始めると、**引っ越しの境目で、同じ手紙が 2 回届いた場合に 2 回処理**してしまいます。

### 重複排除の記憶（`SeenIds`）
**提案：基盤の責任として、新 Core に引き継ぐ（開発者のフックとは別。内部の仕組み）。**

- 理由：
  1. 重複は、旧 Gateway と新 Gateway の両方が同じメッセージを届けることで起きる。同じキー（チャンネルなど）は、**同じ Core に決定的に配送**されるので、各 Core は自分の担当分の重複を見られる。
  2. 問題になるのは、**切り替えの境目をまたぐ重複**（片方が切り替え前に旧 Core へ、もう片方が切り替え後に新 Core へ届く）だけ。
  3. 記憶は小さい（直近 4,096 件の ID。数十 KB 程度、上限あり）。切り替えの瞬間に、旧 Core が新 Core へ、**写しを 1 回渡せば**よい。
- 失敗したとき：写しの引き渡しに失敗しても、**更新は止めない**（記憶が空の新 Core で続ける）。境目の短い間に、まれに重複が起き得ることを、警告ログと文書に明記する。（開発者の任意引き継ぎの失敗は、DDR-0001 に従って更新を中止する。これは別扱い。）
- 切り替えの境目を、**1 つの切り替え番号（epoch）**で決めて、旧・新の Gateway が同じ規則で配送先を決める（Gateway の更新で使っている番号の仕組みと同じ考え方）。
- **配送先は、キーから決定的に決まる**（`(key ^ (key >> 22)) % Core の数`。`src/src/worker.rs` の `dispatch_key*`、2691・3062 行など。コードで確認済み）。同じキーは、旧 Gateway でも新 Gateway でも同じ番号の Core に届くので、上の前提が成り立つ。**注意：Core の数を変えると配送先の計算が変わる**。無停止の差し替えは、Core の数を変えない更新に限る（数を変えるときは、別の扱いが要る。未設計）。

### デモ状態（`!count`、`!job`）
**提案：基盤の特別扱いをやめ、デモ自身が「任意の引き継ぎフック」を使う（自分たちが最初の利用者になる）。**

- 理由：DDR-0001 の「業務状態は開発者が指定する任意の引き継ぎ」と一貫する。`!count` は、基盤の機能ではなく、**サンプルの Bot の状態**。基盤が裏で特別に面倒を見ると、責任の境界がぼやける。
- 副産物：フックの設計を、実際に使って検証できる（`on_handoff`／`on_restore` は仮名。API は未決定）。
- 暫定：フックが実装されるまでは、Core の更新で、`!count` が戻る（現在の「botd 再起動＋保存済みスナップショットからの復元」）。

### 決めてほしいこと
- 上の 2 点（重複排除の記憶は基盤が引き継ぐ／デモ状態はフックを使う）でよいか。
- 「記憶の引き継ぎに失敗しても更新を続ける」でよいか（それとも、止めるか）。

### 作業量・リスク
- 重複排除の記憶の引き継ぎ：小〜中（Core 同士の IPC に、小さい転送を追加。capability の交渉が要る）。
- リスク：境目の重複は、ゼロにはならない（exactly-once は保証しない）。

## 提案 2：通常運用で止まったハンドラへの対処（DDR-0002 の方向で進める）

### 平易な例
お店で、レジ係が 1 人、作業が終わらず固まったとします。**自動でそのレジ係を帰らせる**（自動再起動）のではなく、まず**「どのレジが、何分固まっているか」を店長（運用者）が画面で見られるようにして**、店長が必要なときに「そのレジを閉める」操作ができるようにします。

### 提案する進め方（段階。各段階を独立して実装・検証できる）

| 段階 | 内容 | 作業量 | DDR |
|---|---|---|---|
| **P1：診断を daemon から照会できる** | Core が、未完了の要求の要約（経過時間、件数、Bot・シャード・Core・世代）を、daemon に報告する。`botctl status`／`inspect` に表示する。いまは `core-N.log` の 1 行だけ | 小〜中 | 0002、0003 |
| **P2：閾値を設定できる** | `[core.handler_timeout] warning_after`（既定 30 秒）などを、設定ファイルから。いまはコード内の定数 | 小 | 0003、0004 |
| **P3：Core 単位の管理操作** | `botctl core restart BOT --shard N --core K`（仮名）。**対象の世代を確認**、権限（admin）の検査、監査の記録、**再起動の連続を防ぐ制限**、更新処理との競合防止を付ける。プログラム用 API も、同じ daemon の制御プロトコル（認証つき）で | 中 | 0002 |
| **（保留）自動** | 一定時間で自動の再起動／停止。**DDR で合意されていない**。P1〜P3 が動いた後、実運用の様子を見て、別の判断にする | — | 0003、0004 |

### 設計上の注意（DDR から）
- **プログラムが直接 OS の `kill` をしない**（DDR-0002）。管理操作は、daemon を通す。
- 診断に、**処理名・登録位置**を載せるのは、P1 の後で検討する（DDR-0003：非同期タスクの「いま止まっている行」は特定できない場合がある。秘密・内容を出さない方針との両立が要る）。
- **中断された処理は「結果不明」になり得る**ことを、操作の応答・ログ・API に明示する（DDR-0003）。

### 決めてほしいこと
- 「診断を出し、運用者が管理操作で対処する」（P1→P2→P3）で進めてよいか。
- 自動再起動は、合意していない案として保留でよいか。
- 最初に P1 から着手してよいか（私の推奨）。

### 作業量・リスク
- P1 は、Core から daemon への報告の経路が要る（既存の Health の応答を拡張するか、新しい問い合わせにするか）。IPC の後方互換（古い Core・新しい Gateway の混在）に注意が要る。
- P3 は、誤って正常な Core を止めない確認（世代・状態）が肝心。

## 提案 3：`03-core-hot-swap.md` の書き換え（DDR-0001 に合わせる）

### 現在の 03 との違い
- 現在の 03：「キーごとに担当を固定し、旧 Core の処理が終わったら、**状態を必ず新 Core に引き渡す**」。
- DDR-0001：**状態の引き渡しは任意**。正常な更新では、旧 Core が受け付けた処理を終わらせ、**新 Core の準備後に配送先を切り替える**。

### 書き換え後の骨子（案）

1. **準備（切り替え前。やり直せる）：** 新 Core を別の IPC ソケットで起動（Bot の token は渡さない）。健全性の確認と capability の交渉。開発者が指定した場合だけ、**任意の引き継ぎ**（`on_handoff` で旧 Core がスナップショットを出し、`on_restore` で新 Core が受け取る）。**ここで失敗したら、更新を中止し、旧 Core のまま稼働を続ける**（DDR-0001 の 5）。
2. **切り替え（境目）：** 切り替え番号（epoch）を上げ、新しい処理の配送先を新 Core にする。基盤が持つ重複排除の記憶を、新 Core に渡す（提案 1）。**この境目より後の失敗は、切り戻せない**ので、別に定義する（下記）。
3. **旧 Core の退役：** 新規の受け付けを止め、処理中のタスクが終わるまで待つ（draining）。**退役タイマー**（既定は警告のみ。`auto_stop` は任意、既定オフ。DDR-0004）。終わったら、旧 Core を停止。
4. **切り替え後の失敗（DDR で未決定の部分への提案）：**
   - 新 Core が落ちたら、**通常の Core の障害と同じ**扱い（botd が再起動し、保存済みのスナップショットから復元）。切り戻しはしない。
   - 旧 Core が drain 中に落ちたら、未完了の処理は**結果不明**として記録する（自動の再実行はしない）。

### 決めてほしいこと
- この骨子でよいか。特に、「切り替え後の失敗は切り戻さず、通常の障害として扱う」でよいか（DDR-0001 の 5 の、未決定だった部分）。
- 私が 03 を、この内容で書き換えてよいか。

## 私のおすすめの順序（1 台のサーバーで運用する前提）

1. 提案 2 の **P1**（診断の照会）と **P2**（閾値の設定）：作業が小さく、実機で止まったときの原因追跡に直結する。
2. 提案 3 の書き換え（文書のみ）と、提案 1 の決定。
3. Core の無停止差し替えの実装（提案 1・3）。シングルの完成後。
4. 提案 2 の **P3**（Core 単位の管理操作）。

「シングルの完成」の条件（`decisions-needed.md` の D2）は、別に決めてもらう。
