# 04. 複数ホスト（シングルを完成させてから）

## 方針（ユーザーの指示）

- 既存のライブラリやアルゴリズムで、目的に合うものを使って設計する（独自の合意アルゴリズムは作らない。`AGENTS.md` の方針）。
- **シングル／マルチを設定で切り替えられる**形にする。
- **いまは設計だけ。シングルを完成させてから実装する。** 後からマルチを作るときに困らないよう、シングルの開発中にルールを守る。

## 現状（確認済み）

- 複数ホストでの本番運用は**できない**。過半数の合意（quorum）と lease は、試験用のシミュレーションと、実験的な Raft（OpenRaft 0.9.26）があるだけで、本番起動は拒否される（出典：`docs/known-limitations.md`）。
- Identify の予算は、1 つの botd の中だけで管理している。
- **設定の形は、すでにクラスタを意識している**：`bots.toml` の `[cluster] id / mode = "standalone"`、`[node] id`、`[[bots.shard_placement]] shard_id / primary`（担当ノード）。
- **番号（epoch）で古い所有者を締め出す仕組み**は、Gateway の更新で実機確認済み。複数ホストの「所有者の交代」にも同じ考え方が使える。

## シングルの開発中に守るルール（後から困らないため）

1. **所有者の判定は、1 つの窓口（関数・型）を通す。** 「このホストで動いている」を、あちこちで暗黙に仮定しない。
2. **プロトコル（通信の約束）に、ファイルのパス、PID、ホスト固有の値を混ぜない。** 識別には、Bot ID、シャード番号、世代、epoch を使う。
3. **番号（epoch）による締め出しを、すべての「所有権を持つ操作」に付ける。** 旧所有者の書き込みを拒否できること。
4. **状態の保存は、保存先を差し替えられる形にする**（ローカルファイルから、共有の保存先へ）。
5. **Identify の予算の管理は、窓口を 1 つにする**（プロセス内の管理から、共有の管理へ差し替えられる）。
6. **設定の切り替え（`mode`）を、実際に「standalone」だけで動かすテストを維持する**（マルチを入れたときに、シングルが壊れないこと）。

## 既存の部品の候補（選定は未決定）

| 候補 | 用途 | 確認済みか |
|---|---|---|
| OpenRaft（すでに実験的に統合） | 過半数の合意とログの複製 | 試験用に統合済み。本番統合は未検証 |
| etcd、Consul など外部の仕組み | 所有者を決めるロック／リースを、番号付きで発行 | 未調査 |
| データベースのロック、Redis など | 簡易なリース | 未調査（二重所有の防止の保証を要確認） |

選定の観点：分断時に二重に動かない保証（フェンシングトークン）、運用の手間（シングルのときは何も要らないこと）、障害時の挙動。

## 決めること

- 外部の仕組み（etcd 等）を前提にするか、組み込みの Raft にするか。→ シングル完成後に、設計書（`docs/multi-host-design.md`）で比較する。
- 「ホスト障害時の自動の引き継ぎ」をどこまで求めるか（手動でよいのか）。
