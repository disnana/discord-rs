# DDR-0001〜0005 と、既存資料・現在のコードとの突き合わせ（2026-11-17）

DDR-0005 の「次回の進め方」に従い、`discussion-records/` の合意（DDR-0001〜0004）を読み、**既存の資料（この `design-decisions/` の 01〜08、`decisions-needed.md`）と、現在のコード**との食い違いをリストアップした。

**注意（DDR の指示どおり）：** 食い違いは、黙ってどちらかに合わせず、ここに差分として記録する。既存資料の本文は、下の「提案する修正」を**ユーザーが確認するまで**書き換えない（先頭に「DDR で更新された」という注記だけを加えた）。

## 1. DDR の内容と、現在のコードの実態（確認済み）

| DDR の合意 | 現在のコード | 差 |
|---|---|---|
| 0001：正常な更新で、旧 Core が処理を完了し、新 Core が新しい処理を担当する（drain） | **分離（separate）モードの Core 更新は、botd の再起動が必要で、未実装**（`docs/known-limitations.md`）。組み込み（embedded）の Worker 更新には「旧世代の処理と応答を保持しつつ新世代へ配送」する仕組みがある | 分離モードで未実装 |
| 0001：業務状態の引き継ぎは任意（フック）。強制しない | 状態は Gateway が確認済みスナップショット（`core-state.json`）に保存し、再起動時に復元する（`!count`/`!job` のデモ状態のみ）。**任意の引き継ぎフックはない** | 未実装 |
| 0002：停滞を Daemon 側から確認できる（CLI、警告、対象 Core、経過時間） | 警告は **Core の標準エラー（`core-N.log`）に 1 行出るだけ**。`botctl` や daemon の `status` で、停滞した要求を**照会できない** | 未実装 |
| 0002：開発者がプログラムから警告を利用でき、権限内で Core の停止・再起動を要求できる共通の管理インターフェース | `botctl` の操作は **Bot／シャード単位**（`start\|stop\|restart\|gateway-update BOT [--shard N]`）。**Core 単位の停止・再起動の管理操作はない**（手動の `kill -9` と、botd の自動再起動のみ）。プログラム用 API もない | 未実装 |
| 0003：旧 Core の、長引いている処理の診断（どの処理か、開発者コードのどれか） | 警告は経過秒数と未完了件数だけ（`要求が 30 秒以上完了していません（経過 N 秒、未完了 M 件）`）。**処理名・登録位置は出ない**（秘密と内容を出さない設計のため） | 診断の情報が不足 |
| 0003、0004：警告の閾値を設定できる | **30 秒（警告）、5 秒（確認間隔）、300 秒（再警告の間隔）は、コード内の定数**（`src/src/worker.rs`）。設定できない | 設定機構なし |
| 0004：旧 Core の退役タイマー（draining の経過時間）、任意の自動停止 | 旧 Core の退役という段階自体がない（分離モードで Core 差し替えが未実装のため） | 未実装 |
| 0004：処理単位のタイマーと退役タイマーを別に設定 | 処理単位の観測（警告のみ）だけがある | 片方のみ |

**一致している点：** 処理の打ち切りをしない（警告のみ）、既定の警告 30 秒（DDR-0004 の設定例 `warning_after = "30s"` と同じ値。ただし DDR の値は例示）。

## 2. 既存資料との食い違い

### 2-1. `decisions-needed.md` の D1（B3 の選択肢）
- D1 の選択肢 **b「一定時間で、その Core を自動再起動」** は、DDR-0003、0004 が**合意していない**もの（「旧 Core を自動再起動することは合意していない」）。DDR-0005 も「D1 の『通常の障害でハングした Core の自動再起動』と、旧 Core の『退役時の任意停止』は別問題」と書いている。
- DDR で合意したのは **「更新中の旧 Core の退役時に限った、任意の自動停止（再起動ではない。既定オフ）」**。
- **提案：** D1 を 2 つに分ける。
  - **D1-a（通常運用で、止まったハンドラ）：** a 観測のみ（現状。実装済み）／b 自動再起動（未合意）／c コピーで作業してコミット（未合意）。DDR の方針で最も近いのは「診断を出し、運用者が管理操作で対処する」。
  - **D1-b（更新中の旧 Core の退役）：** DDR-0003、0004 で方針が決まっている（既定は非破壊で警告のみ、`auto_stop` は任意）。**残る判断は、既定の秒数と、設定の単位など**（DDR-0004 の未決定事項）。

### 2-2. `01-stuck-handler.md`
- 「対応案 B（自動再起動）」を、「**DDR で合意されていない案**」と注記する。
- 「気づく」の段階に、**DDR-0002 が求める要件（Daemon から照会、診断情報、開発者向け API）が未実装**であることを追記する（上の表）。

### 2-3. `03-core-hot-swap.md`
- 骨子の手順 3〜4 は、「**キーごとに担当を固定し、旧 Core の処理が終わったら、状態を新 Core に引き渡す**」と、状態の引き渡しを前提にしている。
- DDR-0001 は、「**状態の引き渡しは全 Bot に強制しない。任意（開発者が指定）。** 正常な更新では、旧 Core が受け付けた処理は旧 Core で完了し、新 Core の準備後に、新しい処理の配送先を切り替える」。
- DDR-0005 も、「03 の『キーごとに状態を必ず渡す手順』は、任意引き継ぎという合意と調整が必要」と指摘している。
- **提案：** 03 の骨子を、DDR-0001 に合わせて書き換える。「必須の状態引き渡し」を「**任意の引き継ぎ（フック）**」にし、「旧 Core が drain して終了、新 Core が新規を担当」を基本の経路とする。

### 2-4. 未解決の論点（DDR の責任分界と、基盤自身のデモ状態）
- DDR-0001 は「業務状態の意味・永続化・冪等性は開発者の責任。ただし基盤自身の配送・更新の不具合は開発者に転嫁しない」とする。
- 一方、**基盤自身が Core のメモリに持っている状態**（`!count`、`!job` のデモ。`SeenIds` の重複排除の記憶）は、**基盤の責任の側**に当たる。新 Core が新規を担当し旧 Core が drain する間、これらをどう扱うか（新 Core が空から始まるか、保存済みのスナップショットから始めるか、`SeenIds` を渡すか）は、**DDR で決まっていない**。
- **ユーザーの判断が必要：** 基盤が持つ状態（重複排除の記憶など）の、新旧 Core 間の扱い。

### 2-5. `02-copy-on-commit-state.md`
- DDR のどれにも、この案（コピーで作業してコミット）への言及はない。DDR-0004 は「個別ハンドラのタイムアウトで処理を自動キャンセルすることは合意していない」。
- **提案：** 02 の先頭に「DDR で合意された案ではない」と注記する（内容は変えない）。

### 2-6. `unverified-items.md`
- DDR-0005 は、「実機検証の最新状況は再確認する。文書記載時点から進んでいる可能性がある」と書いている。**今夜書いた `unverified-items.md` は 2026-11-16 22 時時点**で、Oracle の放置（20:46 JST 開始）の結果は、まだ含まれない。
- DDR-0005 の指摘（nonce の利用範囲と、SDK 対応・実機動作を別々に検証する）は、`08` の調査で既に分けて書いている（SDK は確認済み：`enforce_nonce` なし、`payload_json` で補える。実機動作は未確認）。

## 3. 新たに分かった要件（今後の実装の候補）

DDR から導かれる、**これまで私の設計メモになかったもの**。いずれも未実装で、優先順位は未決定。

1. **停滞診断を daemon から照会できる管理面。** `botctl` に、停滞した要求（Bot、シャード、Core、世代、経過時間）を表示する照会（例：`botctl status` の拡張）。→ DDR-0002、0003
2. **警告の閾値を設定ファイルで変えられる。** `[core.handler_timeout] warning_after`、`[core.retirement_timeout]`。→ DDR-0004（設定名は例示）
3. **Core 単位の管理操作**（権限・世代の確認・監査つき）と、プログラム用 API。→ DDR-0002（「プログラムが直接 OS プロセスを kill することを基本設計としない」）
4. **処理の識別情報（処理名・登録位置）**を診断に含める。→ DDR-0003。**注意：** 非同期タスクが「いま止まっている行」を常に特定できるとは限らない（DDR-0003 の注意）。秘密・内容を出さない方針との両立が要る。
5. **任意の引き継ぎフック（`on_handoff` / `on_restore` は仮名）**。→ DDR-0001（API 名・型・順序は未決定）。
