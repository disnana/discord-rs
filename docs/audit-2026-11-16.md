## 9. 再監査 第7回（`64081fd`）の5件への実装対応

以下はコードと試験の追加まで。今回の作業ではビルド・cargo・試験を実行していない。統合担当による WSL でのコンパイル・試験と、Oracle／実 Discord での検証は別途必要。

1. **復旧用 Identify 枠**：候補が存在する間と、有効化失敗後の復旧許可まで、同じ Bot の他 Shard の起動を `Pending` にする。通常の履歴・間隔・上限を使い、復旧許可／確定／有効化前の中止で保護を解除する。停止・復旧回路の最終失敗も保護を残さない。別 Bot は独立。Core 不要の単体試験で、他 Shard の手動・自動起動が枠を消費せず、対象の復旧が最後の枠を使う経路を追加した。
2. **監査末尾のメモリ使用量**：8 KiB のバッファで逆方向に検索し、退避する断片は最大 64 KiB。長い断片も元の末尾全体を切り詰め、退避省略を警告する。大きい正常な履歴を読み直さない検査と、長い末尾の上限・切り詰めの試験を追加した。
3. **FIFO と再 open**：監査の読込・修復は検証済みの read/write + append 記述子を使う。チェックポイントは read-only を維持し、open 後の種別・サイズ・デバイス・inode を照合する。0400 の読込試験を追加した。チェックポイントを open 直前に FIFO へ差し替えられる競合は残し、`known-limitations.md` に記載した。
4. **退避の再試行**：退避のコピー済み位置と記述子を記憶し、同期・切り詰め失敗後は続きから再開する。`.corrupt` への追記は 1 MiB まで。保留された終端監査の再試行失敗後は 1 秒空ける。切り詰め未完了の状態での再試行、上限到達後の修復、再試行間隔の試験を追加した。修復状態は揮発性で、複数プロセスや外部変更との排他は保証しない。
5. **同期だけの再試行**：デバイス・inode・長さに加えて、保存したオフセットのレコード内容を確認する。消失・変更なら同じシリアライズ済みバイト列を再追記する。同じ inode の切り詰め後に長さが戻る場合と、単なる後続追記では重複しない場合を試験に追加した。

これは修正後の合格判定ではない。特にチェックポイントの FIFO 競合、同期 I/O、プロセスをまたぐ競合、既知の停止ハンドラの制約は残る。

## 10. 再監査 第8回（`ed8f21d`）への実装対応

有効化に失敗した Shard が復旧用 Identify を待っている間に更新を再要求すると、全 Shard の再起動抑止と復旧待ちが互いを妨げる問題に対応した。新規 `gateway-update` の受付で、同じ Bot に復旧用の予約があれば、操作登録と `hold_restart` より前に拒否する。予約は消さず、復旧完了後の再要求を促す。別 Bot の受付と既存の操作 ID の照会は従来どおり。

ControlPlane の受付を直接通す回帰試験を追加した。2 Shard の片方に予約がある場合の反復拒否、再起動抑止と操作登録の漏れがないこと、別 Bot の受付、予約解除後に同じ操作 ID で受け付けられることを検査する。Core や子プロセスは起動しない。今回の作業では cargo・ビルド・試験は実行せず、差分と UTF-8 の読戻しのみ確認した。WSL での実行確認は統合担当へ引き継ぐ。
